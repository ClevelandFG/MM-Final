# 分阶段实施计划

本文档记录项目的实施计划，分成各个阶段执行，部分内容可并行实现。

---

## 0. 项目目标理解

本项目要在题面给出的县域道路网络上，为从节点 `O` 出发并返回 `O` 的多组巡视任务设计路线。必须巡视节点包括乡（镇）节点 `A`–`R` 与村节点 `1`–`35`，辅助道路节点 `U01`–`U05` 只承担道路连接作用。

四个原始问题可统一抽象为带节点服务时间的多旅行商/车辆路径类问题：

- 第 (1) 问：固定 3 组，优化总路程，并兼顾路线均衡。
- 第 (2) 问：给定 `T=2h`、`t=1h`、`v=35km/h` 与 24 小时上限，寻找最少组数及对应最佳路线。
- 第 (3) 问：巡视人员足够多时，寻找理论最短完成时间与对应路线。
- 第 (4) 问：固定组数时，分析 `T`、`t`、`v` 改变对路线与目标值的影响。

`docs/theories.md` 提供欧拉图、奇偶点与扫雪问题思路，可作为建模类比：它强调图结构、重复路程、连通分区与均衡目标。但本项目并非必须遍历所有边，而是必须访问所有乡镇村节点，因此后续实现应以“必访节点 + 最短路闭合路线 + 多组划分”为主，欧拉思想主要用于解释图论背景和可能的扩展讨论。

## 1. 两条并行工作线

### 工作线 A：后端建模与优化算法

负责人侧重数学状态、参数校验、核心算法、计时与可测试接口。

主要任务：

- 建立道路网络、节点类型、边权、必访点集合的数据模型。
- 实现原始 TSV 读取、图连通性校验、权重合法性校验。
- 实现全源或按需最短路，得到必访节点之间的闭合路线距离矩阵。
- 定义优化方法接口，先实现可解释的基线方法，再逐步加入改进算法。
- 实现路线、路线组、目标函数、完成时间、均衡性指标与分步骤计时。

交付物：

- 后端核心模块；
- 单元测试与小图回归测试；
- 可被实验脚本和 GUI 调用的稳定服务接口。

### 工作线 B：实验评估、可视化与报告支撑

负责人侧重复现实验、方案比较、图表输出、GUI/报告展示。

主要任务：

- 设计第 (1)–(4) 问的实验配置与结果表结构。
- 实现批量实验调度、随机种子管理、结果导出与运行耗时记录。
- 设计路线图、分组表、耗时分解图、参数敏感性图。
- 在后端接口稳定后实现最小 GUI 或展示页面，只负责输入参数、启动求解、展示路线与图表。
- 整理论文/报告所需的文字素材、图表和复现实验说明。

交付物：

- 实验脚本与结果模板；
- 可视化输出；
- 面向最终报告的路线方案与敏感性分析材料。

两条线的接口约定：工作线 A 输出结构化的 `RoutePlan`、`Route`、`RouteMetrics`、`ExperimentResult` 等概念；工作线 B 不直接改写数学状态，只消费后端返回结果并负责展示。

## 2. 语言选择建议与决策门槛

语言尚未最终确定。当前建议先倾向 Python，理由是图算法、实验调度、可视化和数学建模迭代更快，也更适合 TDD 与报告生成。C++ 的优势在于性能和类型约束，但本题图规模较小，性能风险暂不构成首要瓶颈。

推荐决策：

- 首选 Python 完成 0.x 可行版本；
- 若后续算法扩展到大量随机搜索、元启发式或大规模实例，再评估是否引入 C++ 加速核心；
- 一旦确定语言，应补充对应工具链文件、测试命令和代码规范。

该选择影响工程结构和依赖管理，属于需要用户确认的架构决策；确认后可视情况写入 ADR。

## 3. 分阶段实施

### 阶段 0：工程初始化

目标：

- 建立工程级目录；
- 固化原始路网数据；
- 初始化 Git 仓库并推送远程；
- 沉淀术语、改动记录和实施计划。

完成标准：

- `git status` 干净；
- 远程仓库包含初始化内容；
- `docs/context.md`、`docs/changes.md`、`docs/implementation-plan.md` 已更新。

### 阶段 1：数据模型与读取校验

目标：

- 用 TDD 建立道路网络读取、节点分类、必访点集合和权重校验。
- 校验 `O`、`A`–`R`、`1`–`35`、`U01`–`U05` 的语义边界。

完成标准：

- 能从 `data/raw/road_network.tsv` 构造内存图；
- 能报告节点数量、边数量、必访点数量和辅助点数量；
- 非法节点、负权重、断连图有测试覆盖。

### 阶段 2：路径与耗时基础能力

目标：

- 实现最短路矩阵；
- 定义路线闭合距离、节点停留时间、行驶时间、总耗时；
- 建立分步骤计时接口。

完成标准：

- 任意必访节点之间可查询最短路径距离和实际节点序列；
- 单条路线可计算总路程、行驶时间、停留时间和总耗时；
- 测试覆盖乡镇、村、辅助节点停留时间差异。

### 阶段 3：固定 3 组路线优化

目标：

- 解决第 (1) 问：固定 3 组，给出总路程短且均衡的路线。
- 先实现可解释基线，再实现改进方法。

完成标准：

- 输出 3 条从 `O` 出发并返回 `O` 的路线；
- 所有必访点被覆盖且不重复分配；
- 输出总路程、各组路程、均衡性指标和运行耗时。

### 阶段 4：24 小时约束下的最少组数

目标：

- 解决第 (2) 问：在 `T=2h`、`t=1h`、`v=35km/h` 下寻找满足 24 小时的最少组数。

完成标准：

- 可从组数 1 开始递增搜索；
- 对每个候选组数输出是否可行、最大耗时和路线方案；
- 给出最少组数对应的推荐路线。

### 阶段 5：人员足够多时的最短完成时间

目标：

- 解决第 (3) 问：不限组数时，寻找理论最短完成时间与相应路线。

完成标准：

- 明确组数增加时的下界、可行路线与停止条件；
- 输出最短完成时间、使用组数和路线方案；
- 解释结果与停留时间、往返距离的关系。

### 阶段 6：参数敏感性分析

目标：

- 解决第 (4) 问：固定组数时，分析 `T`、`t`、`v` 变化对路线的影响。

完成标准：

- 支持批量参数网格或指定参数集；
- 输出路线结构变化、目标值变化和瓶颈路线变化；
- 生成报告可用图表。

### 阶段 7：展示层与最终报告支撑

目标：

- 根据后端稳定接口实现最小 GUI 或展示入口；
- 汇总实验结果、图表和文字说明。

完成标准：

- GUI 只负责参数输入、求解触发和结果展示；
- 报告材料能够复现实验命令和关键输出；
- 所有核心结论均有数据或图表支撑。

## 4. 当前待确认问题

1. 编程语言：建议 Python 优先，C++ 作为后续性能加速备选。
2. GUI 范围：建议先不做完整 GUI，等后端接口和实验输出稳定后再做最小展示层。
3. 优化目标优先级：第 (1) 问建议采用“总路程优先，均衡性作为次级目标或约束”的词典序目标。
4. 报告风格：建议实验输出从一开始保留可复现参数、随机种子和计时记录，方便最终论文整理。
